# Доступ к хостам

Контроллер запускает `ansible-playbook`, поэтому ему нужно то же, что и Ansible:
ключ или пароль и решение про host keys. Ничего из этого проект не изобретает —
но где именно должен лежать доступ, зависит от способа установки, и это не
очевидно.

*English version: [docs/connecting-hosts.md](../connecting-hosts.md)*

Всё описанное ниже проверено запуском; контейнерный путь покрыт тестом
`tests/test_integration_container.py`, который гоняет CI.

## Куда кладётся ключ

Сервис работает под непривилегированным пользователем, и ssh смотрит в домашний
каталог этого пользователя. Не в ваш.

| Установка | От кого | Домашний каталог | Ключ положить в |
|---|---|---|---|
| Контейнер | uid 1000 (`ansible-mcp`) | `/var/lib/ansible-mcp` | `/var/lib/ansible-mcp/.ssh/id_ed25519` |
| deb-пакет | `ansible-mcp` | `/var/lib/ansible-mcp` | `/var/lib/ansible-mcp/.ssh/id_ed25519` |
| stdio, запускает клиент | вы | ваш домашний | `~/.ssh/id_ed25519`, как обычно |

Ключ по стандартному пути находится сам, инвентарю упоминать его не нужно. Любое
другое место придётся назвать через `ansible_ssh_private_key_file`.

**Права обязательно 600.** ssh игнорирует ключ, доступный группе или всем, и
прогон падает с `Permission denied (publickey)` — довольно запутанный способ
узнать про режим файла. Проверено: при 644 ключ отбрасывается с `bad
permissions`.

## Контейнер

Смонтировать ключ только для чтения по стандартному пути:

```bash
docker run -p 8080:8080 \
  -v ./data:/data \
  -v ./secrets/id_ed25519:/var/lib/ansible-mcp/.ssh/id_ed25519:ro \
  -e ANSIBLE_MCP_API_KEY="$(openssl rand -hex 32)" \
  ansible-mcp
```

На Linux владельцем файла должен быть uid 1000 или root: ssh откажется от ключа,
принадлежащего кому-то ещё.

```bash
sudo chown 1000 ./secrets/id_ed25519 && chmod 600 ./secrets/id_ed25519
```

Docker Desktop на macOS подменяет владельца сам, поэтому там этот шаг выглядит
лишним — и не является таким.

Рабочий пример лежит в `docker-compose.yml` под профилем `controller`: он
монтирует ключ, ждёт два тестовых SSH-хоста и слушает 8080.

```bash
make keygen
ANSIBLE_MCP_API_KEY=$(openssl rand -hex 32) docker compose --profile controller up -d --wait
```

После этого достаточно инвентаря, который про ключи ничего не говорит:

```ini
[hosts]
ansible_host_1
ansible_host_2

[hosts:vars]
ansible_user=root
```

## deb-пакет

Пакет создаёт пользователя `ansible-mcp` и его каталог состояния. Ключ кладётся
в `.ssh` этого пользователя и принадлежит ему:

```bash
sudo install -d -o ansible-mcp -g ansible-mcp -m 700 /var/lib/ansible-mcp/.ssh
sudo install -o ansible-mcp -g ansible-mcp -m 600 \
  ~/.ssh/id_ed25519 /var/lib/ansible-mcp/.ssh/id_ed25519
sudo systemctl restart ansible-mcp
```

В юните стоит `ProtectHome=true`, так что сервис не прочитает ничей домашний
каталог, даже если инвентарь на него укажет. `/var/lib/ansible-mcp` — его
единственный путь с правом записи.

## Пароли вместо ключей

Ansible берёт их из инвентаря, и `sshpass` установлен в образе именно для этого:

```ini
[hosts:vars]
ansible_user=deploy
ansible_password=...
ansible_become_password=...
```

Оба имени содержат `password`, поэтому значения вырезаются из вывода
инструментов, сообщений об ошибках и журнала аудита (см.
[архитектуру](architecture.md)). Две вещи при этом остаются верными: инвентарь
хранится вместе с задачей, то есть пароль лежит в базе открытым текстом, и всё,
что напечатает Ansible в форме, которую редакция не распознаёт, может утечь.
Ключ лучше.

Передача через переменные (`variables={"ansible_password": "..."}`) работает и
редактируется точно так же.

## Host keys

По умолчанию ssh отказывается от неизвестного хоста — это желаемое поведение и
оно же останавливает первый прогон. Два честных варианта:

**Дать файл `known_hosts`.** Правила те же, что для ключа: домашний каталог
сервисного пользователя.

```bash
ssh-keyscan -H host1.example.com > known_hosts
sudo install -o ansible-mcp -g ansible-mcp -m 644 \
  known_hosts /var/lib/ansible-mcp/.ssh/known_hosts
```

В контейнере — смонтировать в `/var/lib/ansible-mcp/.ssh/known_hosts`.

**Отключить проверку, только для лаборатории.** В окружении процесса:

```bash
ANSIBLE_HOST_KEY_CHECKING=False
```

или на уровне инвентаря:

```ini
[hosts:vars]
ansible_ssh_common_args=-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null
```

Что этим отдаётся: доверенным становится любой хост, ответивший по адресу, — то
есть всякий, кто способен вмешаться в соединение, может выдать себя за ваши
серверы и собрать то, что отправляет плейбук, включая пароль из инвентаря.
Тестовые хосты в `docker-compose.yml` так и делают, потому что они
пересобираются постоянно и доступны только на loopback. Настоящему парку так
делать не стоит.

## Где доступы не хранятся никогда

- **Не в конфигурации провайдера.** Значение, похожее на credential, отвергается
  при добавлении провайдера; конфигурация называет переменную окружения
  (ADR-0006).
- **Не в образе.** Ключ попадает монтированием или установкой, никогда через
  `COPY`.
- **Не в каталоге прогона после прогона.** Инвентарь и файл переменных удаляются
  по завершении, потому что задача и так их хранит.

Но они **есть в базе**: `Task.inventory_snapshot` и `Task.variables` хранят то,
что было передано прогону, потому что без этого его не воспроизвести. Относитесь
к файлу базы соответственно.

## Когда не работает

| Симптом | Обычно это |
|---|---|
| `Permission denied (publickey)` | Права не 600, или владелец чужой, или хост не авторизует этот ключ |
| `Load key ...: bad permissions` | Права 644, ssh вообще пропустил ключ |
| `Host key verification failed` | Нет записи в `known_hosts`, а проверка включена |
| `UNREACHABLE ... Connection timed out` | Маршрутизация, а не доступы: у контейнера своя сеть |
| Из вашей консоли работает, из сервиса нет | Вы смотрите в свой `~/.ssh`, а сервис — нет |

`get_task_logs` отдаёт ошибку ssh дословно, так что нужная строка есть в выводе
упавшей задачи.
