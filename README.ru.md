# ansible-mcp

Минималистичный Ansible-контроллер с интерфейсом MCP — для ИИ-агентов.

Даёте ему плейбук и инвентарь; он выполняет их и хранит историю, логи и артефакты
каждого прогона. Один процесс, один файл SQLite, один контейнер. Ни сервера БД,
ни брокера сообщений, ни парка воркеров.

*English version: [README.md](README.md)*

## Зачем

Запустить Ansible на десятке хостов просто. Запускать его *программно* — уже нет,
и как только это понадобилось, выбор становится тяжёлым: AWX и Ansible
Automation Platform требуют PostgreSQL, Redis, RabbitMQ, Receptor и на практике
Kubernetes. Для пятидесяти хостов такой control plane стоит дороже задачи,
которую решает.

А ИИ-агенту, управляющему инфраструктурой, нужен интерфейс, рассчитанный на
машину. REST API, спроектированный под человека с браузером, — это глубокие
графы объектов и десяток вызовов ради запуска одной задачи; агенту нужна горстка
понятно названных глаголов.

Это и есть проект: **тупой исполнитель** с интерфейсом под агента. Он не пишет
плейбуки и не решает, что запускать, — и то и другое делает вызывающий агент.
См. [docs/ru/concept.md](docs/ru/concept.md).

## Быстрый старт

Ниже версия в три строки; [руководство пользователя](docs/ru/user-guide.md) —
тот же путь с разбором каждого шага и с тем, что делать, когда не работает.

Самый короткий путь — stdio, когда процесс запускает сам клиент:

```bash
poetry install
poetry run ansible-mcp        # говорит на MCP через stdin/stdout
```

В Claude Code или любом MCP-клиенте:

```json
{
  "mcpServers": {
    "ansible-mcp": {
      "command": "poetry",
      "args": ["run", "ansible-mcp"],
      "env": { "ANSIBLE_MCP_DATA_DIR": "/tmp/ansible-mcp" }
    }
  }
}
```

Контейнером, с отдачей по HTTP:

```bash
docker build -f Containerfile -t ansible-mcp .
mkdir -p data && sudo chown 1000:1000 data     # образ работает под uid 1000
docker run -p 8080:8080 -v ./data:/data \
  -e ANSIBLE_MCP_API_KEY="$(openssl rand -hex 32)" ansible-mcp
```

Ключ здесь не опционален: контейнер слушает не на loopback, а сервер
отказывается отдавать неаутентифицированный эндпоинт, исполняющий плейбуки.
Установка на хост — в [упаковке](packaging/README.md).

## Инструменты

| Инструмент | Что делает |
|---|---|
| `run_playbook` | Запускает прогон и возвращает идентификатор; прогон идёт в фоне. `check=true` — сухой прогон: хосты опрашиваются, но ничего не меняется |
| `syntax_check_playbook` | Разбирает плейбук и говорит, валиден ли он, ни к чему не подключаясь |
| `get_task_status` | pending, running, success, failed или cancelled, с временем и кодом выхода |
| `get_task_logs` | Что напечатал Ansible, по умолчанию хвост, секреты вырезаны; `after_line` листает вперёд без перечитывания |
| `cancel_task` | Останавливает стоящий в очереди или идущий плейбук; нужен `confirm=true` |
| `list_tasks` | Недавние прогоны, новые первыми, с фильтром по статусу |
| `save_playbook` / `list_playbooks` / `get_playbook` / `delete_playbook` | Плейбуки по имени, чтобы прогон не тащил текст |
| `add_provider` / `list_providers` / `get_inventory` / `delete_provider` | Откуда берётся инвентарь |

Провайдер — небольшой плагин, отдающий инвентарь: `static` встроен, остальные
регистрируются через группу entry points `ansible_mcp.providers`. Облачные
провайдеры — следующие в плане.

## Чего он сознательно не делает

- **Нет RBAC и мультитенантности.** Один ключ закрывает экземпляр.
- **Нет горизонтального масштабирования.** Один узел, параллельность ограничена
  семафором.
- **Нет веб-интерфейса.**
- **Нет генерации плейбуков.** Это работа вызывающего агента, а LLM-слой, который
  был в прототипе, удалён, а не перенесён.

Каждый пункт — решение с обоснованием и отвергнутыми альтернативами в
[журнале решений](docs/adr/INDEX.md). Упереться в эти границы — сигнал переходить
на полноценную платформу, и именно они держат проект маленьким.

## Безопасность: API-ключ равен доступу к шеллу

Прочитайте это до того, как выставлять эндпоинт куда-либо.

**Кто держит API-ключ, может исполнить произвольный код на хосте контроллера** —
от имени пользователя, под которым работает сервис. Не через уязвимость, а
через саму функциональность. Плейбук с `hosts: localhost` или строка инвентаря
с `ansible_connection=local` выполняются на самом контроллере, а контроллер
создан выполнять любой переданный плейбук: он их не разбирает, не оценивает и не
ограничивает ([ADR-0004](docs/adr/0004-dumb-executor.md)).

Поэтому относитесь к ключу так же, как к SSH-доступу на этот хост. Ключ один на
весь экземпляр, отдельных идентичностей вызывающих нет, и журнал аудита
фиксирует, что было сделано, но не кем.

Что уменьшает радиус поражения сегодня:

- Запускать под непривилегированным пользователем. Контейнер и deb-пакет так и
  делают; ручная установка должна тоже.
- Давать этому пользователю только нужные SSH-доступы и никакого sudo на
  контроллере.
- Не выставлять эндпоинт в сеть без необходимости. У транспорта stdio порта нет
  вообще, а привязке к loopback ключ не нужен: дотянуться до неё уже значит быть
  на этой машине.

По-настоящему это лечится запуском каждого плейбука в контейнере, а не на хосте.
Такое решение принято и описано в
[ADR-0008](docs/adr/0008-execution-environments.md) — и **не реализовано**:
колонка в базе есть, кода нет. Пока его нет, сказанное выше и есть вся модель
безопасности, и этот раздел существует, чтобы никто не узнал об этом на своём
опыте.

## Работа над проектом

```bash
poetry install
poetry run task tests        # 250 тестов
poetry run task lint         # ruff + ruff format + mypy
make integration             # плейбуки на реальных хостах по SSH
poetry run task eval         # справляется ли локальная модель с этим сервером
```

Eval-харнесс здесь не украшение: он читает схемы инструментов из живого сервера
и измеряет, выбирает ли модель правильный инструмент. Несколько описаний
инструментов и весь слой приведения аргументов появились потому, что он сначала
их провалил. См. [evals/README.md](evals/README.md).

Участникам — человеку или агенту — начинать с [AGENTS.md](AGENTS.md).

## Состояние

Ядро работает: прогоны, отмена, таймауты, восстановление после падения,
хранилище плейбуков, провайдеры, редакция секретов, журнал аудита и проверяемый
токен. Ещё нет: REST-поверхности, облачных провайдеров, изоляции выполнения в
образе и файла лицензии — см. план работ.

## Лицензия

Пока отсутствует, то есть использовать, изменять и распространять код никто не
вправе. Планируется Apache-2.0; добавление упирается в вопрос о правообладателе.
